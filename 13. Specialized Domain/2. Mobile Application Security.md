# Mobile Application Security — Practical Cheat Sheet

## 1. Mobile Pentesting Workflow

**Recon → Static Analysis → Dynamic Analysis → Reporting**

- **Static:** Inspect APK/IPA, source code, manifests, secrets, permissions, and configuration without running the app.
    
- **Dynamic:** Run the app, inspect network traffic, logs, local storage, and runtime behavior.
    
- **Reporting:** Document the vulnerability, evidence, impact, reproduction steps, and remediation.
    

## 2. Application Package Analysis

### Android — APK

**Identify the file**

```
file app.apk
unzip -l app.apk
```

**Extract package contents**

```
mkdir apk_extract
unzip -q app.apk -d apk_extract
```

**Decode manifest and resources**

```
apktool d app.apk -o apktool_out
```

**Decompile Java/Kotlin bytecode**

```
jadx -d jadx_out app.apk
```

**Important files**

- `AndroidManifest.xml` — permissions, activities, services, receivers, providers, exported components.
    
- `res/values/strings.xml` — application strings and sometimes exposed secrets.
    
- `assets/` — bundled configuration, databases, and other resources.
    
- Decompiled source — authentication logic, API endpoints, keys, and hardcoded credentials.
    

## 3. iOS — IPA Analysis

An IPA is a ZIP-based application package.

```
file app.ipa
unzip -l app.ipa
mkdir ipa_extract
unzip -q app.ipa -d ipa_extract
```

**Locate** `**Info.plist**`

```
find ipa_extract -name Info.plist
```

On macOS, inspect it using:

```
plutil -p "ipa_extract/Payload/App.app/Info.plist"
```

**Search for secrets**

```
grep -RniE 'api[_-]?key|password|secret|token|https?://' ipa_extract
```

**Important files**

- `Info.plist` — application configuration and security settings.
    
- `Payload/*.app/` — application bundle.
    
- `*.plist` — may contain credentials, tokens, URLs, or internal configuration.
    
- Application binary — can reveal strings and logic during reverse engineering.
    

## 4. Hardcoded Secrets

**Search decompiled Android code**

```
grep -RniE 'api[_-]?key|password|secret|token|client_secret' jadx_out
```

**Search extracted package files**

```
grep -RniE 'api[_-]?key|password|secret|token|http://' apktool_out
```

**Inspect binary strings**

```
strings app_binary | grep -iE 'api|password|secret|token|https?://'
```

**Look for**

- API keys and access tokens.
    
- Database usernames/passwords.
    
- Hardcoded encryption keys.
    
- Internal URLs and development endpoints.
    
- Credentials inside `.plist`, JSON, XML, and database files.
    

**Gotcha:** A public API key is not automatically a critical vulnerability. Check its permissions, restrictions, scope, and potential impact. Client-side secrets should never provide unrestricted access to privileged backend operations.

## 5. Android Manifest — Security Checks

Inspect the decoded manifest:

```
cat apktool_out/AndroidManifest.xml
```

**Check for**

- Excessive permissions.
    
- Activities, services, receivers, or providers exposed unnecessarily.
    
- Exported components handling sensitive data.
    
- Debuggable production builds.
    
- Insecure backup or network-security settings.
    

Search for exported components:

```
grep -nE 'android:exported="true"|android:debuggable="true"|android:allowBackup="true"' \
apktool_out/AndroidManifest.xml
```

**Attack surface:** An exported component may be callable by another application. Verify whether access controls exist and whether the component exposes sensitive data or privileged functionality.

An exported component is not automatically vulnerable.

## 6. iOS Configuration — App Transport Security

Inspect `Info.plist` for:

```
NSAppTransportSecurity
NSAllowsArbitraryLoads = true
```

When `NSAllowsArbitraryLoads` is enabled, App Transport Security's normal restrictions on insecure connections can be relaxed.

**Why it matters:** The application may communicate over unencrypted HTTP, exposing sensitive information to interception.

**Test:** Identify affected endpoints and determine whether credentials, tokens, or other sensitive information are sent without adequate transport protection.

**OWASP mapping:** M5 — Insecure Communication; potentially M8 — Security Misconfiguration.

## 7. MobSF — Automated Static Analysis

**Start MobSF with Docker**

```
docker run -it --rm -p 8000:8000 \
opensecurity/mobile-security-framework-mobsf:latest
```

Open the MobSF web interface at:

```
http://127.0.0.1:8000
```

Upload the APK or IPA and review the generated report.

**Prioritize**

- Hardcoded secrets and credentials.
    
- Manifest and `Info.plist` misconfigurations.
    
- Insecure network configuration.
    
- Weak cryptography.
    
- Insecure storage indicators.
    
- Exported components and excessive permissions.
    
- Binary protection findings.
    

**Workflow:** MobSF report → verify manually → establish impact → document evidence.

Automated findings require validation; a scanner warning alone does not prove exploitability.

## 8. Dynamic Analysis

### Traffic Interception

Use Burp Suite or a similar intercepting proxy to examine application requests and responses.

**Check**

- HTTP instead of HTTPS.
    
- Credentials or tokens in requests.
    
- Sensitive information in API responses.
    
- Unexpected third-party endpoints.
    
- Insecure session management.
    

### SSL/TLS Pinning

Certificate pinning restricts which certificates an application trusts. It can prevent a testing proxy from intercepting traffic.

**Tool:** Objection, built on Frida, supports runtime exploration and testing of application behavior, including assessment of certificate-pinning controls.

Pinning is a defensive control, not a vulnerability by itself.

### Runtime Instrumentation

**Tool:** Frida.

Useful for examining:

- Authentication and authorization checks.
    
- Sensitive data held in memory.
    
- Biometric-gated functionality.
    
- Runtime handling of tokens and application secrets.
    

Verify whether security decisions are enforced by the backend rather than relying exclusively on client-side checks.

### Insecure Logging

Inspect logs during application use. Look for passwords, API tokens, personal information, and sensitive API responses.

**OWASP mapping:** M9 — Insecure Data Storage.

## 9. Common Mobile Vulnerabilities

|Finding|What to investigate|OWASP category|
|---|---|---|
|Hardcoded credentials|Source code, resources, configuration|M1 — Improper Credential Usage|
|Weak authentication|Login logic, token expiry, re-authentication|M3 — Insecure Authentication/Authorization|
|HTTP transmission|Credentials or tokens sent without adequate encryption|M5 — Insecure Communication|
|Missing binary protections|Obfuscation, tamper detection, root/jailbreak checks|M7 — Insufficient Binary Protections|
|Exported components|Sensitive activities or providers without access control|M8 — Security Misconfiguration|
|Sensitive local storage|Plaintext files, databases, logs, cached responses|M9 — Insecure Data Storage|

## 10. Remediation Checklist

- Remove hardcoded passwords and privileged secrets from application packages.
    
- Restrict API keys and rotate exposed credentials.
    
- Enforce HTTPS and secure transport configuration.
    
- Minimize permissions and restrict exported components.
    
- Protect sensitive local data using appropriate platform security mechanisms.
    
- Avoid logging credentials, tokens, and personal data.
    
- Perform authentication and authorization checks server-side.
    
- Use secure cryptography and key management.
    
- Apply obfuscation and tamper protections where appropriate.
    
- Validate findings from automated tools before reporting them.
    

## Core Workflow

**Extract APK/IPA → Inspect manifest and** `**Info.plist**` **→ Decompile and search for secrets → Scan with MobSF → Verify configuration and exported components → Test runtime traffic, storage, and authentication → Document impact and remediation.**
