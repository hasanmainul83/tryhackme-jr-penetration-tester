
The application trusts software, updates, or data without verifying their integrity or origin.

## Common Examples

- Insecure deserialization
    
- Unsigned or unverified updates
    
- Untrusted plugins or dependencies
    
- Modified CI/CD artifacts or configurations
    
- Untrusted JSON, templates, or binaries
    

## Insecure Deserialization

Converting serialized data back into objects can be dangerous when the input is untrusted and insufficiently validated.

**Example:** User-controlled Python `pickle` data → Deserialization → Potential code execution.

## Key CWEs

- **CWE-502** — Deserialization of Untrusted Data
    
- **CWE-345** — Insufficient Verification of Data Authenticity
    
- **CWE-494** — Download of Code Without Integrity Check
    

## Real-World Examples

- **SolarWinds SUNBURST (2020)** → Malicious code inserted into a legitimate, digitally signed software update.
    
- **CVE-2017-9805 (Apache Struts)** → Insecure XML deserialization enabled remote code execution.
    
- **CVE-2026-47856 (Spring Integration)** → Verify the reported vulnerability details before relying on this example.
    

## Prevention

- Verify updates and artifacts using digital signatures.
    
- Avoid unsafe native deserialization; allow-list permitted types when necessary.
    
- Secure CI/CD pipelines and verify dependencies.
    
- Monitor integrity violations and suspicious activity.
    

## Mindset

Can an attacker modify something the application assumes is trusted?
