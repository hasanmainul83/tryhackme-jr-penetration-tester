Now we move from the common web flaws into vulnerabilities that usually need a little more digging—sessions, authentication, file handling, command execution, and APIs.


Session management is how the app remembers you after login. Instead of sending credentials on every request, you get a cookie or a Bearer token.

Two flavors: **Cookie-based** (browser sends it automatically) or **Token-based** (client sends `Authorization: Bearer TOKEN`).

---

## **Enumeration / Inspection**

```
# Inspect headers
curl -i http://TARGET/
```

Look for:

```
Set-Cookie: PHPSESSID=...
Secure
HttpOnly
SameSite
Expires
```

```
# Login, save cookie
curl -c cookies.txt -X POST -d "username=USER&password=PASS" http://TARGET/login

# Reuse session
curl -b cookies.txt http://TARGET/dashboard

# Manual session
curl -b "PHPSESSID=SESSION" http://TARGET/dashboard

# Bearer token
curl -H "Authorization: Bearer TOKEN" http://TARGET/api/user
```

**Test flow:** Login → Capture session → Reuse → Modify/Delete → Logout → Try old session → Check expiry and authorization.

## **The Real-World Attacks (2026)**

**1. JWT (The Modern Token)**

Don't just replay it. Decode it and inspect the header and claims.

- **`alg=none`:** Change the algorithm to `none`, remove the signature, and see whether the server incorrectly accepts it.
- **Weak HMAC:** `hashcat -m 16500 jwt.txt wordlist.txt`
- **`kid` injection:** Test whether the application unsafely uses the `kid` value to load a signing key. File-path or special-value tricks only work against vulnerable implementations.
- **Revocation:** Log out or change the password, then replay the old JWT. If the application is supposed to revoke it but still accepts it, that is a session-management flaw.
- **Tool:** `jwt_tool`

**2. Session Fixation**

App doesn't rotate the session ID after login? Fix a session ID **before the victim authenticates**. If the same ID survives authentication, the attacker may be able to reuse that authenticated session.

**3. Cookie Tossing / SameSite Bypass**

`SameSite=Lax` still sends cookies on top-level cross-site **GET** navigation. If a state-changing action accepts GET, it may be CSRFable.

Also check subdomains for **cookie tossing**—a subdomain may be able to set or overwrite a parent-domain cookie when cookie attributes allow it.

**4. Token Storage (Where is it?)**

- `localStorage` → Hunt XSS.
- `HttpOnly Cookie` → JavaScript can't read the cookie; investigate CSRF protections, `SameSite`, and other cookie/security controls.

**5. CORS Misconfigurations (The SPA Killer)**

```
curl -H "Origin: https://evil.com" -I http://TARGET/api/user
```

Look for:

```
Access-Control-Allow-Origin: https://evil.com
Access-Control-Allow-Credentials: true
```

A dangerous CORS policy can allow an attacker-controlled origin to read authenticated responses when credentials are accepted.

**6. OAuth / OIDC**

- Missing `state` → CSRF risk in the OAuth flow.
- Weak or exploitable `redirect_uri` validation → Can lead to authorization-code or token leakage in vulnerable flows.
- Token leak via `Referer` → Check whether sensitive values appear in URLs that may be sent as referrer data.

**7. Cookie Prefixes**

- `__Secure-` → Cookie must use `Secure`.
- `__Host-` → Requires `Secure`, `Path=/`, and **no `Domain` attribute**.

These prefixes help prevent certain cookie-setting and cookie-tossing attacks.

## **The Real Bug (Authorization)**

The session says _who_ you are. It doesn't say _what_ you can do.

Log in as User A. Grab the session. Try to access User B's resources. If it works, it's an API-level IDOR / broken authorization issue.

**Tool:** **Autorize** (Burp). Low-priv session, replay high-priv requests, flag responses that should have been denied.
