

Broken authentication occurs when the application's authentication logic can be bypassed or abused, allowing access without the correct credentials.

## **Username Enumeration**

The app reveals which usernames are valid through differences in messages, status codes, response sizes, or response timing.

**Confirm the difference manually first:**

```
curl -s -X POST \
-d "username=admin&email=x&password=x&cpassword=x" \
-H "Content-Type: application/x-www-form-urlencoded" \
http://TARGET/customers/signup
```

**Look for:**

- `already exists`
- `username taken`
- `invalid username`

**Fuzz usernames:**

```
ffuf -w /usr/share/wordlists/SecLists/Usernames/Names/names.txt \
-X POST \
-d "username=FUZZ&email=x&password=x&cpassword=x" \
-H "Content-Type: application/x-www-form-urlencoded" \
-u http://TARGET/customers/signup \
-mr "username already exists"
```

**Also test:** Login, Password reset, Signup, Registration APIs.

Username enumeration can also appear through differences in status code, response length, or timing.

## **Password Brute-Force & Credential Stuffing**

**Brute force** → Try many passwords against one account.  
**Credential stuffing** → Try previously leaked username/password pairs against another service.

**Brute-force a known user:**

```
ffuf -w /usr/share/wordlists/SecLists/Passwords/Common-Credentials/10-million-password-list-top-100.txt \
-X POST \
-d "username=admin&password=FUZZ" \
-H "Content-Type: application/x-www-form-urlencoded" \
-u http://TARGET/customers/login
```

Use the application's known failed-response status, size, or words to filter results.

**Rate-limit testing:**

- Repeated requests → Observe when blocking starts.
- Check whether the limit is per IP, account, session, or device.
- Check whether trusted proxy headers affect the limit.

A spoofed `X-Forwarded-For` header only matters when the app or reverse proxy incorrectly trusts attacker-controlled forwarding headers. It is not a universal rate-limit bypass.

## **Password Reset Logic Flaws**

Password-reset functionality is another authentication boundary. Test whether the app properly validates the reset token, user identity, and reset flow. OWASP recommends reset tokens be random, sufficiently long, tied to the correct user, and invalidated after use.

**Host Header Injection**

If the app builds password-reset URLs from an untrusted Host or forwarding header, the generated link may point to an attacker-controlled host.

```
POST /forgot-password HTTP/1.1
Host: attacker.com

email=victim@example.com
```

The vulnerability exists when the application trusts that header while generating the reset URL. OWASP specifically recommends not relying on the Host header when creating reset URLs.

**Parameter Pollution**

Give the app multiple values for the same parameter and see which value different parts of the app use.

```
POST /customers/reset

email=victim@example.com&email=attacker@example.com
```

Also test: `?email=victim@example.com&email=attacker@example.com`

Different frameworks may handle duplicate parameters differently.

**Race Conditions**

Reset tokens should normally be single-use and invalidated after successful use. Test whether multiple simultaneous requests using the same token can bypass that logic.

Get reset token → Send multiple requests simultaneously → Check whether the token can be accepted more than once.

## ** Cookie Manipulation**

Sometimes the application trusts information stored directly in the client-side cookie.

**Insecure Flags**

Check: `Secure`, `HttpOnly`, `SameSite`.

- `HttpOnly` prevents JavaScript from reading the cookie.
- `Secure` restricts the cookie to HTTPS.
- `SameSite` controls when the browser sends the cookie in cross-site requests.

A missing `SameSite` attribute does not automatically mean CSRF is exploitable, but it removes one layer of CSRF protection.

**Predictable Values & Encoding**

Check whether the cookie contains: Plaintext, Base64, Hash, Role, User ID, Privilege information.

**Decode or reproduce the value:**

```
# Base64
echo 'BASE64_VALUE' | base64 -d

# MD5
echo -n 'VALUE' | md5sum
```

**Modify and replay:**

```
curl -b "session=MODIFIED_VALUE" http://TARGET/dashboard
```

Example: `role=user` → `role=admin`. This only works when the server trusts the modified client-side value without proper integrity/authentication checks.

## Advanced 

### **JWT — JSON Web Token**

`Authorization: Bearer TOKEN` can contain a JWT, but not every Bearer token is a JWT. A JWT normally has three dot-separated parts: `HEADER.PAYLOAD.SIGNATURE`.

Decode it and inspect: `alg`, `typ`, `iss`, `aud`, `sub`, `exp`, `nbf`, `role`, `scope`.

**Common things to test:**

- `alg=none` → Test whether the verifier incorrectly accepts an unsigned JWT. Modern libraries generally reject this by default, so this is mainly a legacy/misconfiguration check.
- **Weak HMAC Secret** → Attempt offline cracking when the token uses an HMAC algorithm.
- **Algorithm / key confusion** → Test whether the server incorrectly allows incompatible signing algorithms or key types.
- `kid` **Injection** → Check whether `kid` is unsafely used in filesystem, database, or key-selection operations. It is not automatically exploitable just because `kid` exists.
- **Issuer / audience confusion** → Test whether a token issued for one service or audience is accepted by another.
- **Token lifetime / revocation** → Replay expired or logged-out tokens and check whether the app still accepts them.

**Crack a weak HMAC secret:**

```
hashcat -a 0 -m 16500 jwt.txt wordlist.txt
```

**Tool:** `jwt_tool`

`alg=none`, key confusion, and unsafe `kid` handling are implementation flaws—not normal behavior of a properly configured modern JWT verifier.

### **MFA Bypass**

MFA adds another authentication factor, but the implementation can still contain flaws.

**Premature session issuance**

```
Login → Session cookie issued → OTP verification
```

Check whether the pre-MFA session can already access protected functionality.

**MFA fatigue**

Repeated push notifications may trick a user into approving one. This is a social-engineering attack rather than a cryptographic MFA bypass.

**Adversary-in-the-Middle (AiTM)**

A phishing proxy can relay the authentication flow and capture session material after authentication in vulnerable deployments.

- **Tools:** `Evilginx3`, `Modlishka`.
- **How it works:** Evilginx3 sits as a reverse proxy between the victim and the real site. The victim visits your URL, sees the real login page, enters credentials and OTP, and Evilginx captures the fully authenticated session cookie. You import that cookie into your browser and you're in.
- **Key pentest question:** Does the app bind the session to the device (fingerprint, IP)? If not, the stolen cookie is enough.

### **OAuth / SSO Flaws**

OAuth security testing should focus on the integrity of the authorization flow.

**Missing / invalid `state`:**

```
Authorization request → Capture state → Return response → Check whether state is validated
```

The state value is primarily used for CSRF protection in the OAuth flow.

**Redirect URI validation:**

```
redirect_uri=https://trusted.example/callback
```

Test whether the application accepts:

```
https://evil.example/
https://trusted.example.evil.example/
https://trusted.example/callback/../
https://trusted.example@evil.example/callback
https://trusted.example/callback?redirect=https://evil.example
https://trusted.example/callback#https://evil.example
```

The `@` payload is the classic parser confusion bug. The app reads `trusted.example` as the username and `evil.example` as the host. Modern OAuth providers reject this with exact matching, but older implementations still fall for it.

**Token leakage:**

Check whether tokens or authorization codes appear in: URL, Browser history, Logs, Referer, Third-party resources.

OAuth guidance explicitly considers token leakage through browser history and referrer headers.
